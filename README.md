# DS3Probe v4.2

Прокси `dinput8.dll` для Dead Space 3 (Win32). **Ничего не чинит**: собирает данные и по клавишам F9/F11 подменяет вход игры, чтобы найти, где именно ставится потолок скорости поворота камеры («чем быстрее рвёшь мышь, тем меньше эффект, а после порога поворот всегда одинаковый»).

Статус и допущения: `claude/ds3_status.md`. Аудит: `claude/ds3_audit_2026-10-07.md`.

## Что нового в v4.2 (после данных сессии 20261008_214545)

Данные показали: угол камеры `cam+0x20` считается точно (`dψ = −3.94·dt·выход`), а рикошёт рождается позже, на пути «цель → отображаемая ориентация». Проба этого места не видела. v4.2 добавляет:

1. **Дамп памяти** (`TraceN.dump = <смещение hex, может быть со знаком> <длина hex, кратна 4, ≤ 400>`, `TraceN.dumpfrom = K`): при каждом вызове трассировщика пишет блок памяти в `ds3probe_cap_NNN_dump.csv` (`t_ms,id,ptr,слова hex...`). `dumpfrom = K` берёт указатель из регистра base последнего вызова трассировщика K (так Trace4 и Trace5 дампят объект камеры, чей адрес даёт Trace8). Готовый блок: `ds3probe_camdump.cfg.example`.
2. **F5 — «вижу рикошёт прямо сейчас»**: метка времени в `ds3probe_cap_NNN_marks.csv` (писк высокого тона). Работает только внутри захвата (F7…F8).

Опыт (≈10 минут): положи `ds3probe_camdump.cfg.example` как `ds3probe.cfg` рядом с exe; в логе должно быть `DS3Probe v4.2` и `hook: ok` у Trace1..5, 8. Клэмп — F11 до открытого (4 нажатия), F9 в PASS. F7 → 6–8 длинных рывков обычной камерой, **в момент каждого рикошёта жми F5** → F8. Затем то же самое в прицеле (ПКМ зажата), рывки без F5 → F8. Пришли папку сессии.

## Что нового в v4.1 (после данных v4, сессия 20261008_082440)

Что показали данные v4 (подробно: `claude/ds3_analysis_session_20261008_082440.md`, статус: `claude/ds3_status.md`):

- Камеру питает **только** DirectInput (DI-ZERO: выход `FUN_0040D820` = 0 во всех 792 кадрах, камера «как будто мышь выдернули»).
- **Первый потолок найден**: клэмп `±this[3] = 2.0` в `FUN_0040D820`. Формула окна подобрана по логу с ошибкой < 1e-5:
  `X = Σ(сырой стик за окно)`, `выход = clamp(Xb, ±2.0) / (Tb · 30)`; сырой стик = 0.032 на отсчёт мыши. Предел — ~62 отсчёта за окно в ~2 кадра, то есть **~2300–2800 отсчётов/с**, не зависит от FPS (по формуле). Обычный рывок — 26–35 тыс. отсчётов/с, это **в 10–15 раз выше потолка**; клэмп съедает 56–69 % горизонтального поворота в пакете пользователя.
- F11 (клэмп открыт) убирает потолок: выход линеен до 422 отсчётов/кадр (максимум выхода 34.5 против 2.97). Но на резком рывке камера «подклинивает, упирается в невидимое и отскакивает в то же либо примерно то же место». В самом вводе отскока нет (хвост обратного знака ≤ 1.5 %), значит **второй ограничитель — ниже по цепочке**. Кандидаты: (H1) переполнение угла за кадр при одинарной нормировке ±2π и клэмпе углов в `FUN_0073f310`; (H2) проверка `FUN_004fdf60` с откатом состояния камеры; (H3) следящая камера / столкновение (`FUN_0074baa0`). Все три — гипотезы, различаются трассировщиками и лестницей клэмпа ниже.

Изменения v4.1:

1. Трассировщики: `TraceN.base` (регистр-основа), `TraceN.fields` (до 16 смещений полей объекта), колонки `eax`, `base`, `f0..f15` в `_trace.csv`. Хук можно ставить посреди функции (после `CALL`) и читать `eax`.
2. `_sticks.csv`: колонка `caller_hex` — **настоящий** адрес вызывающего `FUN_0040D820` (в v4 колонка `ret_hex` была возвращаемым значением, а не адресом; она осталась). Таблица вызывающих печатается и по F6.
3. `analyze_di.py`: блок **[F]** (сверка модели окна с логом + сколько поворота съедает клэмп) и **[G]** (события-рывки: длительность, пик, сумма, хвост обратного знака); блок **[E]** показывает аргументы/поля трассировщиков как float.
4. `ghidra/DS3_CamChain.py` — скрипт для работы: готовый cfg-блок с трассировщиками (байты берутся из Ghidra сами), дизассемблер вокруг `CALL FUN_004fdf60` в `FUN_0073f310`, константы, декомпиляция цепочки камеры.
5. **F11 теперь лестница клэмпа**: каждое нажатие — следующая ступень `this[3]`: исходный (2) → **6 → 12 → 24 → 1e9 (открыт)** → исходный. Так находится, при каком масштабе выхода стика появляется «упор и отскок» (т. е. где второй ограничитель). Значение клэмпа каждого кадра пишется в `_sticks.csv` (колонка `clamp`), так что ступени можно менять прямо в одном захвате; анализатор: блок **[H]**.

## Зачем v4 (что показали данные v3, сессия 20261007_194254)

1. **Эталон Raw Input в v3 был мёртв** (в `raw_dx` везде нули): DirectInput игры перерегистрировал мышь процесса, и проба лишилась своего потока `WM_INPUT`. Вердикт анализатора «резких движений нет» был артефактом. В v4 эталоном служат счёты DirectInput, проба Raw Input сама не регистрирует и только пишет в лог, кто его регистрирует.
2. **DirectInput и курсорный аккумулятор несут один сигнал** (98 % кадров совпадают точно, отношение сумм 1.02–1.07 на скоростях 1…800 отсчётов/кадр). Сжатия и полки между рукой и этими двумя слоями нет.
3. **Камера вращалась при обнулённом аккумуляторе** (`look = 0` минуту подряд). Значит, камеру питает не путь «курсор → `InputMapper_Update` → `MouseState.look`», а, скорее всего, DirectInput. Потолок сидит **после** DirectInput, внутри игры.

Отсюда режимы F9 теперь подменяют именно вход DirectInput.

## Первый запуск: что должно быть в логе

Лог: `ds3probe_logs\<дата_время>\ds3probe.log` (`latest.txt` указывает на последнюю папку). Каждая сессия — своя папка.

| строка в логе | норма |
|---|---|
| `DS3Probe v4 sha=... attach` | v4, а не v3 |
| `exe MD5=1802f17a...` и `profile: 1.0.0.1 selected by MD5` | оба есть |
| `anchor: OK: ... confirms Mouse_GetState=0040A820` | допустим `FAILED`; `MISMATCH` — хуки Mouse_GetState отключены |
| `Mouse_GetState / Mouse_WndMsg / InputMapper_Update hook: ok` | как в v3 |
| `StickVirt hook: ok`, `StickSmooth hook: ok` | **новое.** `FAILED` — байты функций не совпали, F11 недоступна, `_stickv/_sticks.csv` не будут писаться |
| `exe hooks done: ... stickVirt=1 stickSmooth=1 traces=N` | N = число трассировщиков из cfg |
| `DirectInput8Create ver=... hr=0x00000000`, `hook DirectInput8Create: ok` | есть |
| `DI mouse state: cb=20 lX=... from exe+0x... [ghidra 00XXXXXX]` | **ключевая строка**: игра читает мышь через DirectInput. Пока её нет, F9 пишет `UNAVAILABLE`. Адрес «from» — вызывающий в Ghidra-координатах: это точка входа в потребителя |
| `RegisterRawInputDevices(n=...) from ...` | **новое.** Кто регистрирует Raw Input; если игра не регистрирует — строк нет |
| `1s: ... mode=PASS DI=(sumX,sumY) stickV(max out=... acc_len=... sat=N) stickS(max out=...)` | `DI` — сумма DI за секунду (печатается, когда водишь мышью); `stickV/stickS` — максимумы выходов стик-функций за секунду (появляются, если эти функции вызываются); `acc_len` → 1.0 и `sat` > 0 = упор в круговой клэмп |

## Горячие клавиши (окно игры в фокусе)

| клавиша | что делает | звук |
|---|---|---|
| F5 | (v4.2) метка «вижу рикошёт прямо сейчас» в захвате | 1 высокий |
| F6 | маркер в лог + таблицы «кто вызывает» (user32 и DI-мышь, со стеком вызывающих) | — |
| F7 / F8 | начало / конец захвата (CSV + итоги в лог) | 1 / 2 писка |
| **F9** | режим: **PASS → DI-ZERO → DI-xA(×0.5) → DI-xB(×0.25) → DI-xC(×2.0) → ACC-ZERO → PASS** | 1 / 1 / 2 / 3 / 4 / 5 писков (PASS — один низкий) |
| F10 | условия опыта + список зарегистрированных raw-устройств | — |
| **F11** | **лестница клэмпа** `FUN_0040D820.this[3]`: исходный (2) → 6 → 12 → 24 → 1e9 → исходный; номер ступени и значение — в логе `=== F11: clamp ladder level N/4 ... ===` | ступень 1…4 — 2 писка, тон выше с номером; возврат на исходный — 1 низкий |

Режимы:

- **DI-ZERO** — `lX/lY` из `GetDeviceState` := 0. Камера обязана замереть, если она питается от DI. Если крутится — у неё другой источник.
- **DI-xA / xB / xC** — отсчёты × 0.5 / 0.25 / 2.0 (с дробным остатком, ничего не теряется). Если потолок внутри игры и он по скорости, он сдвинется пропорционально K; если потолок по углу за время, поворот на рывке не изменится.
- **ACC-ZERO** — обнуляется курсорный аккумулятор (путь v3). Нужен только для сверки: камера должна вращаться как обычно.
- **F11** — лестница клэмпа `±this[3]` в сглаживателе стика (v4.1: 6 → 12 → 24 → 1e9). Клэмп 6 пропускает втрое больше, чем исходный 2; на 1e9 выход линеен (в данных v4: до 422 отсчётов/кадр). На какой ступени появляется «упор и отскок» — там и лежит предел следующего ограничителя (в единицах выхода стика).

Страховка: режимы F9 сами возвращаются в PASS через 2 минуты. Подмена касается только отсчётов мыши, игру не ломает.

## Вечерний протокол v4.1 (~40 минут, 75 Гц как у тебя)

Подготовка (один раз): собрать v4.1 в GitHub Actions, заменить `dinput8.dll`. Блок трассировщиков `Trace1..Trace8` из `ds3_camchain_1802f17a.md` (раздел 0, его делает работа в Ghidra) кладётся в `ds3probe.cfg` рядом с exe; **без него лестница клэмпа и все шаги ниже работают**; трассировщики нужны, чтобы различить гипотезы H1/H2/H3 (дают угол за кадр и срабатывание отката). В логе должно быть `DS3Probe v4.1`; если трассировщики включены — `Trace1..Trace8 ... hook: ok` (при `MISMATCH`/`FAILED` пришли лог и не продолжай). Играем в **открытом месте без стен рядом**, потом повторяем у стены.

Пакет движений (паузы > 0.3 с): 10 медленных проводок; 10 коротких рывков (~4–5 см за ~0.1 с); 10 длинных (~15 см за ~0.1 с). Отдельно — **вертикальные** рывки (вверх-вниз).

Главное изменение против прошлого раза: **одна ступень лестницы — один захват, F7/F8 вокруг неё**, и в ответе — что именно ты видишь на каждой ступени. Ступени: **L1 = 6, L2 = 12, L3 = 24, L4 = открыт**; нажатия F11 ведут по кругу L1 → L2 → L3 → L4 → исходный.

| # | действия | что записать |
|---|---|---|
| 1 | В геймплее: **F6** (маркер + таблицы вызывающих), F10 | — |
| 2 | F11 один раз (**L1 = 6**): F7 → пакет (гориз.) → F8 | на этой ступени «подклинивает»: нет / слабо / сильно; рывки короткие / длинные / только самые быстрые |
| 3 | F11 (**L2 = 12**): F7 → пакет → F8 | то же самое |
| 4 | F11 (**L3 = 24**): F7 → пакет → F8 | то же самое |
| 5 | F11 (**L4 = открыт**): F7 → пакет → F8 | то же + **куда** отскакивает: в точку начала рывка / на часть пути / в произвольную; дёргается ли картинка во время рывка; пропадает ли «подклинивание» при очень коротких рывках |
| 6 | Оставить L4 и сделать **вертикальные** рывки: F7 → пакет → F8; затем **у стены** (камера почти упирается в геометрию): F7 → гориз. рывки → F8 | упирается ли вверх/вниз; изменилось ли «подклинивание» рядом с геометрией |
| 7 | F11 до исходного (низкий писк). **F9 три раза до DI-xB (×0.25, 3 писка)**: F7 → пакет → F8; затем **F9 ещё раз до DI-xC (×2, 4 писка)**: F7 → пакет → F8. Режим сам вернётся в PASS через 2 минуты после нажатия F9, поэтому F7 жми сразу и укладывайся в ~100 с (в прошлый раз для xB и xC захватов нет: xB включался без F7, xC не выбирался) | угол рывка и обычной скорости относительно PASS: больше / меньше / равно; есть ли «новый потолок» |
| 8 | F9 до PASS | — |

Если мало времени: достаточно шагов 1, 2, 4, 5 (лестница на 6, 24 и открытом) и 6 (стена).

Если трассировщики включены (файл `ds3probe.cfg` есть), в тех же захватах появятся `_trace.csv` — отдельных действий не нужно.

Что прислать: папку `ds3probe_logs\<сессия>` целиком + наблюдения из колонки «что записать». Анализ: `python tools\analyze_di.py <папка>`; блоки [F] (модель), [G] (рывки), **[H] (ступени клэмпа)** и [E]/`_trace.csv` (трассировщики).

## Анализ

```
python analyze_di.py ds3probe_logs\<сессия>
```

(`analyze_samples.py` — анализатор v3; для данных v4 не нужен.) Блоки:

- **[A]** DI против курсорного пути: совпали ли кадры, сдвиг, отношение сумм по скоростям.
- **[B]** режимы: сработала ли подмена (`out/game ≈ K`, ZERO ≈ 0).
- **[C]** передаточная кривая «вход DI → выход стика» по корзинам скорости; вердикт «линейна / сжатие / ПЛАТО».
- **[D]** выход стика при DI-ZERO / DI-xK: питается ли стик от DI.
- **[E]** трассировщики: число вызовов, `[esp]`/ecx, значения аргументов и полей как float (v4.1).
- **[F]** (v4.1) модель `FUN_0040D820` против лога (ошибка должна быть ~1e-6; иначе формула другая) и сколько горизонтального/вертикального поворота съедает клэмп ±2.0; порог в отсчётах/с.
- **[G]** (v4.1) события-рывки (`|dx| ≥ 8`): длительность, пик, сумма, доля обратного знака внутри и в 8 кадрах хвоста.
- **[H]** (v4.1) лестница клэмпа F11: по каждому значению `this[3]` из `_sticks.csv` — кадры, кадры у потолка, максимум |вых.x|, интеграл |вых.x|·dt. Печатается, только если в захвате встретилось 2+ значения клэмпа.

Самопроверка анализатора на синтетике: `python tests/test_analyze_di.py` (в Actions идёт отдельным шагом и сборку DLL не блокирует).

### Как читать итог

| наблюдение | вывод |
|---|---|
| DI-ZERO: камера замерла | камера питается от DI; потолок между DI и камерой |
| DI-ZERO: камера крутится | есть другой источник (Raw Input? клавиатурная эмуляция?) — смотри строки `RegisterRawInputDevices` и трассировщики |
| xA/xC: угол рывка пропорционален K | потолка по скорости нет; сжатие — в самом коэффициенте/кривой |
| xA/xC: угол рывка не меняется | потолок по углу (клэмп результата или лимит скорости поворота) |
| F11: потолок исчез | причина — клэмп `±this[3]` в `FUN_0040D820`; фикс = менять `this[3]` или обходить клэмп |
| F11: потолок остался | клэмп не тот; [C] по `_stickv.csv`: длина `acc` упирается в 1.0 → `FUN_0040E680` (круговой клэмп) |
| [C]: `ПЛАТО` на выходе стика, на входе линейно | потолок в конвейере «стик»; координаты — в `_sticks.csv` |
| [C]: стик линеен, а камера всё равно упирается | потолок в потребителе стика (камера/лимит скорости поворота): трассировщики на потребителей |

## Трассировщики (новые гипотезы без пересборки)

В `ds3probe.cfg` (см. `ds3probe.cfg.example`): `Trace1 = <адрес из Ghidra>`, `Trace1.bytes = <первые 8+ байт из Ghidra>`, `Trace1.name = подпись`. Хук ставится на вход функции (или на любую инструкцию), пишет `ecx`, `edx`, `eax`, аргументы стека, `.this` dword по `.base` и поля по смещениям `.fields` в `ds3probe_cap_NNN_trace.csv` и в лог. Хук ставится, только если байты совпали. Готовый блок для цепочки камеры печатает `ghidra\DS3_CamChain.py` (раздел 0 отчёта).

## Файлы сессии

- `ds3probe.log` — лог (строки `1s:` раз в секунду).
- `ds3probe_cap_NNN_di.csv` — кадры DI-мыши: `t_ms,raw_dx,raw_dy,game_dx,game_dy,mode,out_dx,out_dy` (`game_*` — что отдал DI, `out_*` — что получила игра после подмены; `raw_*` в v4 не используется).
- `ds3probe_cap_NNN_acc.csv` — кадры `Mouse_GetState` (курсорный путь, как в v3), с кодом режима.
- `ds3probe_cap_NNN_stickv.csv` — вызовы `FUN_0040E680` (виртуальный стик): `x_out,y_out,acc_x,acc_y,active,id`.
- `ds3probe_cap_NNN_sticks.csv` — вызовы `FUN_0040D820`: `dt,x_in,y_in,x_out,y_out,win,blend,clamp,active,w0..w7,ret_hex,caller_hex` (`ret_hex` — возвращаемое значение функции, а не адрес; адрес вызывающего — `caller_hex`, с v4.1; `w0..w7` = `this[4..11]`: текущее и прошлое окно как `x_sum, y_sum, t_sum, n` — четвёртое поле это целое число отсчётов, поэтому печатается как 0.000).
- `ds3probe_cap_NNN_trace.csv` — трассировщики из cfg: `t_ms,id,ecx,edx,ret,a0..a7,t0..t15,eax,base,f0..f15` (hex dword; `ret` — `[esp]`).

## Что не проверено (честно)

- **DLL v4.1 не собиралась автором** (нет Windows-тулчейна; v4 пользователь собрал и запустил без ошибок): проверен только разбор clang (`-fsyntax-only`) с самодельными заглушками заголовков. Ошибка Actions — пришли текст.
- Соглашения вызова `FUN_0040E680` и `FUN_0040D820` (`__thiscall`, порядок аргументов) взяты из декомпиляции Ghidra и могут быть неточными; в логе первые вызовы печатаются, значения должны быть правдоподобными (`dt` ≈ 0.013, `id` 4 или 5, выход в пределах ±1).
- Что стик-функции вообще участвуют в клавиатурно-мышиной камере — **гипотеза**: `id` в рантайме 4/5 (< 0x10), тип устройства KBM (0x12). Если `_stickv/_sticks.csv` пусты или `active=0` — они обходятся, это тоже ответ.
- Режимы DI подменяют только `GetDeviceState` для мыши (`cb=20`). Если игра читает `GetDeviceData`, подмена не сработает: в логе не будет `DI mouse state` и F9 напишет `UNAVAILABLE`.
- `this = ecx` в `InputMapper_Update` и смещения `+0x17C`/`+0x18C` — из 1.0.0.0; самопроверка в логе.
